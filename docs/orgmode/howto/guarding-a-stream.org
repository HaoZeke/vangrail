* Guard a Streamed Answer

Run the deterministic output rails while the answer is still arriving, so a
credential or a refused line never reaches the screen at all.

Use this when you stream tokens to a reader. If you hand over a finished
answer, =Engine#check_output= is all you need and this page does not apply.

(The reason it exists: an output rail on the finished text runs after the
reader has read it, so the most a caller can do at the end is withdraw text
somebody has already seen.)

** Wrap the stream

#+BEGIN_SRC ruby
engine = Vangrail.from_env
guard = Vangrail::StreamGuard.new(engine, user_input: question)

client.stream(prompt) do |chunk|
  verdict = guard.push(chunk)
  break if verdict&.blocked?

  emit(guard.take)
end

final = guard.finish
show_retraction(final.reason) if final.blocked?
#+END_SRC

=push= returns =nil= when there is nothing to say, which is the usual case. It
returns a =Result= when a rail rewrote the buffer or blocked it. A caller that
ignores the return value entirely gets the old end-of-stream behaviour and
nothing worse.

=take= is what to print. It returns only the suffix that has not been handed
out yet *and that a rail has read*: the tail arriving since the last check
waits until a check covers it, or until =finish=. So the visible text lags the
model by up to one interval, which is the price of never showing a line no rail
has seen. A guard that released the tail immediately would stream the
credential and redact it a chunk later. After a redaction that keeps the already-shown prefix, that is the
rewritten tail, not the whole buffer. Do not print =result.content= on every
event: that reprints everything already on screen.

** What runs when

| Rail kind     | When it runs        | Why                          |
|---------------+---------------------+------------------------------|
| deterministic | every 40 characters | microseconds, cannot fail    |
| model-backed  | at =finish= only    | one round trip per chunk is a minute per answer |

Half a sentence is also not the object a grounding rail was written to judge.
Its citation has not been generated yet. Refusing an answer for arriving slowly
would be a worse failure than the one being fixed.

Set the interval with =interval:=. Lower means more checks over shorter text;
the rails are regexps, so the cost is real but small.

** What this buys, exactly

Everything the deterministic rails can see is caught before display. What only
a model can see is caught at the end, as before. A stream guard that implied
otherwise would be the more dangerous object, so it is worth repeating in
whatever your application tells its readers.

** After a block

=guard.content= is the text that was actually shown. The guard stops consuming
once blocked, so pushing more chunks changes nothing and returns the block
again. What to do with the partial text is an application decision. Leaving it
on screen with a note is honest, and removing it is defensible. Pretending the
answer completed is neither.
