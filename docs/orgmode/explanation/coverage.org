* What This Covers, and What It Does Not

A rail list is easy to read as a claim of completeness, which it never is. This
page maps the rails onto the published categories, and it is written so the
gaps are as visible as the coverage: the reader who needs this page is deciding
what else they still have to build.

** Against the OWASP list for language model applications

The 2025 edition, read for a retrieval-augmented documentation assistant. The
categories that assume tool use or an agent loop do not apply to one, and
saying so is more useful than stretching a rail to cover them.

| Category                        | Rails                                        | State |
|---------------------------------+----------------------------------------------+-------|
| Prompt injection                | =Pattern=, =InjectedInstructions=, =Jailbreak=, =Paraphrase=, =Similarity=, =Obfuscation=, =Hidden=, =ManyShot=, plus =Semantic= and =Perplexity= where an endpoint allows them, and =Spotlight= marking with its hierarchy | covered, with the limits below |
| Sensitive information disclosure | =Secrets= on the answer, =PersonalData= on the question, including a labelled Dutch BSN with its checksum | covered for shapes, not for judgement |
| Supply chain                    | none                                         | out of scope; the gem's own answer is a runtime with no dependencies |
| Data and model poisoning        | =Engine#screen= drops a poisoned document rather than failing the turn | partial: a poisoned page that reads as ordinary prose passes |
| Improper output handling        | =Markup=, =Exfiltration=                     | covered for rendering and for outbound URLs |
| Excessive agency                | none                                         | not applicable: no tools, no actions |
| System prompt leakage           | =Canary= for the exact token, =Pattern= and =Paraphrase= for the ask, =PromptLeak= for the answer that reproduces it | covered for verbatim and for reproduction; a summary carrying none of the prompt's words is still a gap |
| Vector and embedding weaknesses | =Engine#screen= at the boundary              | partial: retrieval quality is the application's |
| Misinformation                  | =Grounding=                                  | covered, at the cost of a round trip |
| Unbounded consumption           | =Budget=                                     | covered for size; rate limiting belongs to the server |

** The limits worth repeating

*** Paraphrase beats every pattern, so the patterns are not what reads the text

The jailbreak fingerprints, the injection patterns, and the canary all fall to
a rewrite that means the same thing. =Rails::Paraphrase= is the answer to that
which does not need a model: the text is reduced to concepts first, and what
gets matched is a pair of concepts close together, so a rewording that keeps
the meaning keeps the pair. Measured on twelve reworded asks at five positions,
it catches 60 of 60 where the pattern rails catch 0, and keeps 24 of 24
ordinary pages.

What that does not mean is that rewording is solved. The lexicon is the limit,
and it is a list of words in a file:

- A synonym nobody listed is a miss. "Countermand the guidance issued to you"
  walks past, and the suite asserts that it does.
- A language nobody listed is a miss for every rail here. English and Dutch are
  read; a page in German is prose to all of it.
- The negation scope is a cheap evasion. A negator dropped into the clause has
  a revealing verb read as concealment, and an attacker who reads this page
  knows it.
- Two concepts is a rule about form, not about meaning. A sentence that asks
  for the same thing while naming only one of them is not caught.

The model-backed rails are what remain against those, and a model's verdict is
an opinion rather than a rule.

*** A third language is reported rather than read

=Rails::Language= exists because the honest answer to a page or a question in
German is "nothing here read this". It identifies the language by function
words and returns =passed= with =certain?= false for anything outside the
lexicons, and it never blocks: another language is not an attack. It sits
on the input side as well as on context, so =check_input= cannot certain-pass
a long unread question.

What it does not do is extend coverage. A German page is exactly as unguarded as
it was; the difference is that the result now says so, which is what lets an
application route it somewhere else. Under twelve tokens it stays quiet, so a
short question in an unsupported language passes as certain and is a real hole
rather than a rounding error.

*** The model-backed rails move the limit rather than removing it

=Semantic= and =Perplexity= go past the lexicon by asking an endpoint, and both
bring their own limits, which are different in kind from a missing word.

- Neither threshold ships measured. Cosine scores and log probabilities belong
  to the model in use, so both default numbers are starting points and both
  probe scripts refuse to recommend a threshold when the corpora overlap. A
  deployment that switched these on without running the probe is running an
  uncalibrated detector, which is worse than an absent one because it looks like
  a check.
- =Perplexity= needs an endpoint that will echo and score a prompt, and many
  will not. It reports uncertain there rather than clean, which means the family
  it targets is uncovered and named rather than uncovered and silent.
- =Semantic= sends the text somewhere. On a loopback proxy that is nothing; on a
  third-party endpoint every screened document is a document sent, and that is a
  data-flow decision the application makes rather than a default it inherits.
- Both cost a round trip per check, which is why neither is on by default and
  why the deterministic rails are what run on every turn.

*** The Dutch coverage is a lexicon, not an understanding

Every pattern in this gem is English. The concept lexicon carries Dutch as
well, and it is scored on a Dutch corpus rather than assumed to transfer: 60 of
60 caught, 24 of 24 ordinary Dutch pages kept, and the English pattern rails
catch 0 of the 12 Dutch attacks.

Three pieces of Dutch grammar are handled and worth knowing about, because they
are where a naive port would fail: negation lands after the verb, so the scope
reaches further right than left; a backward reference behind a determiner at
the end of a clause is a noun, which is how /negeer het bovenstaande/ names
the instruction it cancels; and a subordinate clause puts the verb last, so
the ordered override templates also match when the verb is the last token
(/dat je de richtlijnen negeert/) and leave the coordinated handbook sentence
(/volg de richtlijnen en negeer verouderde kopieen/) alone. Anything past
those three is not modelled.

*** An attacker who reads the source wins more often

The published work on adaptive attacks breaks detection-based defences by
optimising against the detector. Every pattern in this gem is public. That is
the right trade for a documentation desk, where the traffic is overwhelmingly
ordinary and the attacks are overwhelmingly copied, and it is the wrong trade
for anything where a motivated attacker is the expected case.

*** A model rail is a model reading an argument written to persuade it

=SelfCheck=, =GuardModel=, =Grounding=, and =Trajectory= all send text to a
model and believe the answer. When the text is a retrieved page, it was written
by whoever wants it believed. Deterministic rails cannot be argued with, which
is why the context side leans on them.

*** Nothing here is a substitute for the application's own defences

An output sanitiser, a rate limit, an authorisation check on retrieval, and a
log a human reads are all outside this gem and all more important than any rail
in it. The rails are a layer, and a layer is what they are worth.

*** The prompt shape helps by about a quarter, and a quarter is not enough

=Spotlight= fences retrieved text and states an instruction hierarchy.
Measured on twelve injections that no deterministic rail in this gem catches,
at 384 trials an arm: a plain prompt was obeyed 95 times, a fenced one 68.
z = 2.38, p = 0.017, difference between 1.3 and 12.8 percentage points.

So it works, and it works by roughly a quarter in relative terms. What it does
not do is prevent obedience. Seventeen percent of these injections still get
through a fenced prompt, and none of them was recognisable to a pattern. That
residual is the gap the model-backed rails and the grounding check exist to
close, and it is why an application running only the deterministic rails is
running a floor rather than a defence.

A first run at 48 trials an arm gave 12 against 8 and would have been written
up as a null result. Same script, smaller sample.

*** Uncertainty is reported rather than hidden

Every rail that could not reach a decision returns =passed= with =certain?=
false. An engine whose endpoint is down keeps its deterministic rails and says
so in every result. That is the one guarantee here worth calling a guarantee:
nothing reports a clean check it did not perform.
